# Инженерный разбор

## Контекст

FB Autoload вырос из реальной задачи: запуск рекламы требует согласованной работы нескольких систем, но ни одна из них не знает состояние всей операции. Загрузка медиа, создание кампании, привязка ресурсов и получение статистики могут завершаться независимо друг от друга.

Продукт собирает этот процесс в одном интерфейсе. Главная сложность — не отправка запросов, а сохранение корректного состояния между ними.

## Схема рабочего приложения

```text
                         Общая кодовая база
                 UI · API · validation · workflow engine
                    /                         \
             Отдельный запуск A          Отдельный запуск B
             AdsPower adapter           Dolphin adapter
             Tracker adapter            Tracker / PWA adapters
             DB A · session A           DB B · session B
             secrets A · bot A          secrets B · bot B
                    \                         /
                         Внешние API
```

Это не микросервисная платформа и не два независимых форка. Общая логика переиспользуется, а процессы и рабочие данные разделены. Такой подход уменьшает дублирование правил, не смешивая доступы и статистику.

## 1. Неизвестный результат — отдельное состояние

**Проблема.** Таймаут после POST не доказывает, что объект не создан.

**Решение.** Сохранять подтверждённые результаты и намерение записи. Перед повтором сверять внешние объекты в правильном контексте кабинета и цепочки. Найденный объект переиспользовать; неполное или неоднозначное чтение не считать доказательством отсутствия.

**Компромисс.** Иногда безопаснее остановить конкретный этап, чем добиться зелёного статуса автоматическим повтором. Гарантировать exactly-once поверх стороннего API без его поддержки нельзя.

**Публичный пример.** `dist/recovery.mjs` показывает эту границу на синтетических данных. Обнаруженное отсутствие тоже не даёт ему права на новый POST: модель требует отдельного решения оператора. Полный production-механизм имеет больше стадий и отдельных политик ошибок.

## 2. Сохранённый прогресс, а не повтор всей задачи

**Проблема.** При сбое в конце большого запуска нельзя начинать заново с загрузки всех файлов.

**Решение.** Сохранённые этапы, точные ID и связи с ресурсами. При разрешённом продолжении переиспользуются проверенные объекты. Отложенная работа хранится вместе со временем выполнения и связью с родительской задачей.

**Компромисс.** Восстановление сложнее простого retry. Оно требует явной модели состояний, проверки идентичности объектов и тестов на отмену, частичное выполнение и потерянные ответы.

## 3. Общая логика без смешивания интеграций

**Проблема.** Копии одного приложения постепенно начинают по-разному генерировать запросы и обрабатывать ошибки. Но общий код не означает общие базы или авторизацию.

**Решение.** Общее ядро для плана, очереди и стадий; адаптеры для провайдеров. Контур задаёт свои пути, настройки, сессии и маршруты уведомлений. Изоляция проверяется отдельно.

**Компромисс.** Изменение общего контракта требует проверки обоих контуров, даже когда дефект проявился только в одном.

## 4. Статус задачи не равен статусу кабинета

**Проблема.** Ошибка авторизации, отсутствие оплаты и телефонная проверка требуют разных действий. Один общий `failed` этого не объясняет.

**Решение.** Раздельное состояние кабинета и текущего запуска, точная причина и результат по каждому кабинету. Подготовленные ресурсы не считаются завершённой кампанией. Неполный отчёт сохраняет собранные факты и показывает пробелы покрытия.

**Компромисс.** UI должен показывать частичные результаты, а не сводить весь процесс к зелёной или красной карточке.

## Разработка с нейросетями

AI использовался как инструмент исследования и разработки, а не как источник истины о состоянии внешних систем. Требования, примеры ошибок и ожидаемое поведение фиксировались в контрактах и регрессионных тестах. Фактический результат проверялся отдельно от успешного ответа на запрос.

Публичная презентация не раскрывает внутренние инструкции, конкретные аккаунты или журнал эксплуатации. Описанные подходы основаны на рабочем проекте, но демонстрационный код не является доказательством безошибочности всей производственной системы.

## Границы этого репозитория

- Презентация и демонстрационный пример работают без сети и учётных данных.
- Обозначения `DEMO`, `campaign-demo` и `media-demo` — вымышленные.
- Здесь нет реальной отправки рекламы, отчётов или расходов.
- Тесты проверяют только опубликованную модель и состав файлов, не production-интеграции.
- Скриншоты, если добавлены, показывают эту презентацию, а не действующие кабинеты.
